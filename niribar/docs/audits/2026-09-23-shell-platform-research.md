Scope: notification integration and the desktop services needed around a Niri-first shell. Local review used Niribar `988f970` and Canopa Notify `1be911d87bf16780c7c7b382f26d571ab9074e2b` at `/home/kevinard/projects/canopa/notify`. Recommendations below are product proposals, not claims that previously scoped bar features are defective. Earlier Niribar findings already fixed in the [remediation](2026-09-23-remediation.md) and [desktop follow-up](2026-09-23-desktop-validation.md) are not reopened here.

## Notification capability already exists

Canopa is substantially beyond a notification prototype. Its selected Desktop Notifications 1.3 profile includes receipt/replacement/closure, sender actions and activation tokens, banners, persistent local history, retained **Requires Attention** state, DND, application/category rules, static images, sound, and safe body links. Capability advertisement accounts for optional runtime services. The compliance record contains executable, renderer, private-bus, and real desktop acceptance evidence; this research did not rerun that full suite. Sources: [Canopa compliance matrix](../../../canopa/notify/docs/freedesktop-notification-compliance.md), [retained-attention decision](../../../canopa/notify/docs/adr/0049-retained-attention-and-sender-lifecycle.md), and [desktop acceptance](../../../canopa/notify/docs/notification-desktop-acceptance.md).

Niribar already hosts the Notification Center through explicit `canopa-v4` configuration. Its adapter enforces bounded JSON lines, version/content validation and generation-owned interactions; rendering supports sections, actions, controls, text styling, local images, links, keyboard reading and native AT-SPI. The provider sends complete replacement pages, preserving notification ownership in Canopa. This is implemented integration, not a proposed future panel. Sources: [transport selection](../../src/config/parse/mod.rs), lines 294–305; [Canopa adapter](../../src/external_panel/canopa.rs), lines 89–132; [provider documentation](../external-panel-providers.md), lines 145–166; [Canopa integration guide](../../../canopa/notify/docs/niribar-panel-provider.md).

The canonical protocol and Niribar's vendored snapshot match: `bash scripts/check-panel-protocol.sh /home/kevinard/projects/niribar`, run from the Canopa checkout, passed during this review. This verifies source agreement, not every installed binary pair. [The script](../../../canopa/notify/scripts/check-panel-protocol.sh) compares `Cargo.toml` and `src/lib.rs`.

## Recommended sequence toward a desktop shell

### 1. Supported Niri session and application lifecycle

Ship a session integration preset and a read-only health command covering Niri environment, the shell and Canopa services, portals, audio, an authentication agent, the locker/idle manager, Secret Service/Secret portal and Xwayland support. Reuse Niri's session setup and systemd user units rather than starting a second process supervisor inside the bar. Niri's session exports the graphical environment and starts session targets; its integration guide supports XDG autostart and services attached to `graphical-session.target`. [Niri getting started](https://niri-wm.github.io/niri/Getting-Started.html), [Niri integration](https://niri-wm.github.io/niri/Integrating-niri.html#autostart).

This goes beyond the existing [Niribar unit](../../contrib/systemd/niribar.service), which correctly attaches one bar process to the graphical session but does not assemble a complete desktop. Test login, logout, failed startup, bar restart and Canopa restart as user journeys. Keep Nix packaging deferred according to the existing owner decision.

Application launch lifetime needs its own boundary. The current “detached” [launch helper](../../src/command.rs), lines 230–237, calls ordinary process spawn; it does not move applications out of the shell service's cgroup. The [unit](../../contrib/systemd/niribar.service) retains systemd's default `KillMode=control-group`, which terminates remaining members when the unit stops. Therefore a child that stays in that cgroup can be killed by a shell restart. This is a source-based inference; no live user service was restarted. Route user application launches through Niri's spawn IPC or distinct application scopes, while retaining bounded cleanup for owned providers/workers. Do not solve application lifetime by weakening cleanup of the entire bar service. [systemd kill semantics](https://raw.githubusercontent.com/systemd/systemd/main/man/systemd.kill.xml), [transient services/scopes](https://raw.githubusercontent.com/systemd/systemd/main/man/systemd-run.xml), [Niri IPC](https://niri-wm.github.io/niri/IPC.html), [Niri spawn](https://niri-wm.github.io/niri/Configuration%3A-Key-Bindings.html#spawn).

### 2. Session controls, locking and power policy

Provide lock, logout, suspend, hibernate, reboot and power-off controls, showing only supported/authorized operations and explaining active inhibitors. Use logind's capability queries and power operations, and an existing session locker/idle daemon initially. A shell Panel is not a secure lock surface: `ext-session-lock-v1` assigns authentication to the locker and requires the compositor to keep the session locked even if that client dies. Coordinate lock readiness with suspend using `PrepareForSleep` and a delay inhibitor; merely issuing a lock command does not prove that locked pixels were presented. [logind API](https://raw.githubusercontent.com/systemd/systemd/main/man/org.freedesktop.login1.xml), [inhibitor lifecycle](https://systemd.io/INHIBITOR_LOCKS/), [session-lock protocol](https://gitlab.freedesktop.org/wayland/wayland-protocols/-/blob/main/staging/ext-session-lock/ext-session-lock-v1.xml).

Idle policy must distinguish inhibition-respecting inactivity from explicit user-input inactivity: version 2 of `ext-idle-notify-v1` provides both. Use this deliberately for display blanking, presentation mode and locking rather than assuming one timer serves every purpose. The upstream protocol files were also inspected from `/usr/share/wayland-protocols/staging/`; the freedesktop GitLab pages were unavailable to the web reader. [idle-notify protocol source](https://gitlab.freedesktop.org/wayland/wayland-protocols/-/blob/main/staging/ext-idle-notify/ext-idle-notify-v1.xml).

Include a session authentication agent in this milestone. Polkit's design explicitly places an authentication agent in the graphical user session. The existing Wi-Fi provider reports authorization-required errors and deliberately does not implement polkit prompts. A complete desktop must supply that dependency. [polkit architecture](https://polkit.pages.freedesktop.org/polkit/polkit.8.html), [Wi-Fi provider contract](../external-panel-providers.md).

The following are proposed additions, absent from the current [Module Kind inventory](../../src/modules.rs), lines 82–94, or broader than the existing implementation. Domain state should remain behind dedicated adapters/providers; Niribar should own placement, keyboard interaction, accessible widgets and presentation.

Introduce a bounded, accessible slider only when implementing audio/brightness needs it. Preserve explicit protocol versions and existing Wi-Fi/Canopa compatibility.

### 4. Desktop compatibility and settings

Treat portals as part of the shipped experience. Niri's current guidance uses GTK as fallback, GNOME for screencasting, and a Secret portal provider; its default file chooser also needs Nautilus or an explicit GTK chooser selection. Provide a consistent configuration and acceptance tests for sandboxed file selection, opening links, screencasting and notifications. Build a custom portal backend only for a specific behavior the standard stack cannot supply. [Niri software requirements](https://niri-wm.github.io/niri/Important-Software.html), [screencasting](https://niri-wm.github.io/niri/Screencasting.html), [portal selection](https://flatpak.github.io/xdg-desktop-portal/docs/portals.conf.html).

Settings should begin with output arrangement/scale and keyboard layout, wallpaper, theme/font/scale preferences, default applications and autostart. For appearance, consume the Settings portal's color-scheme, contrast and related advertised preferences, with explicit user overrides. Avoid claiming to configure the system when only Niribar's colors change. A separate settings application can edit validated configuration; not every persistent settings workflow belongs in a transient Panel. [Niri outputs](https://niri-wm.github.io/niri/Configuration%3A-Outputs.html), [Settings portal](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.Settings.html).

After the foundation, add a command palette combining installed applications, shell actions and Niri windows/workspaces; then clipboard history, removable-media workflows and richer notification search/snoozing if demanded. These are product prioritization recommendations, not dependencies of a functional first session.

## Notification work to leave with Canopa

Native Notification portal v2, inline reply, snoozing, full-text history search and richer grouping should be Canopa features. A native portal integration implements `org.freedesktop.impl.portal.Notification` behind the portal frontend; it does not replace the public `org.freedesktop.portal.Desktop` service. The frontend supplies an application identity and negotiates backend capabilities. [Backend API](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.impl.portal.Notification.html), [public Notification v2](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.Notification.html).

The existing GTK bridge already delivers ordinary notifications to Canopa. Its recorded installed-stack result is v1, so v2 features cannot be inferred merely from the frontend package version. That September 3 result is historical evidence, not a new probe of today's session. Check the negotiated interface version and `SupportedOptions` in future acceptance. [Canopa bridge research and measurements](../../../canopa/notify/docs/xdg-notification-portal-v2.md).

Complete the existing [manual matrix](../manual-validation.md), then add the cross-component journeys: clean login, restart shell without closing launched applications, resume into an already locked session, delayed/cancelled authorization, hardware hotplug, audio route changes, portal file picker/screencast, notification action delivery through the installed pair, and bar/Panel/provider keyboard and screen-reader navigation.
