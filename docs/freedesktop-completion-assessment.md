# Freedesktop completion assessment

**Historical assessment before the completion implementation.** Its remaining-work list describes baseline `8898be0`, not the current code. See the [current compliance matrix](freedesktop-notification-compliance.md), [desktop evidence](notification-desktop-acceptance.md) and [release verification](notification-release-verification.md).

Assessed 2026-09-16 against the official Desktop Notifications specification and the current repository. This is a completion assessment, not a new implementation plan or a claim that every existing test was rerun.

The [latest official publication](https://specifications.freedesktop.org/notification/latest/) remains version 1.3, published 2024-08-18. The core protocol is substantially implemented and has executable evidence. The approved project target is broader: a complete static profile with safe links, body images, persistence, accessible interactions, and operational acceptance. That target remains unfinished. See the [approved scope](../.scratch/freedesktop-completion-review/PLAN.md) and [current execution tracker](../.scratch/freedesktop-completion-review/IMPLEMENTATION.md).

## What “support the specification” requires

The [protocol](https://specifications.freedesktop.org/notification/1.3/protocol.html) defines four methods, closure/action signals, nonzero IDs, atomic replacement, closure invalidation, and timeout behavior. Capabilities are optional but their advertisement is a promise of behavior; `actions` promises access to sender actions, and `sound` entails file playback and suppression hints. `persistence` promises retention through acknowledgement, user removal, or sender recall. Static and animated icon capabilities are mutually exclusive. Activation-token signals are optional.

The [basic design](https://specifications.freedesktop.org/notification/1.3/basic-design.html) requires only the Notifications interface for this specification; automatic D-Bus activation is optional. A native portal backend, inline replies, snoozing, conversation grouping, and every desktop environment are not requirements of the Notifications 1.3 interface.

[Markup support](https://specifications.freedesktop.org/notification/1.3/markup.html) is optional, and hyperlinks and embedded body images are explicitly optional. [Hints](https://specifications.freedesktop.org/notification/1.3/hints.html) are generally optional too. Therefore the missing `body-hyperlinks`, `body-images`, and `persistence` advertisements do **not**, by themselves, make the current subset nonconforming. They do leave the project's selected static profile incomplete.

## Remaining work, in priority order

1. **Make the advertised actions reliably reachable and accessible.** [Banner projection](../crates/canopa-notify/src/presentation.rs#L2530) takes only two named actions; it handles default activation separately. The [overflow indicator](../crates/canopa-notify/src/presentation.rs#L1987) is a label, not a route to more actions. The complete live action list depends on a compatible Niribar Center and a successful provider projection. Complete keyboard reading/scrolling, held-key behavior, provider-overflow/pagination, and the supported host-availability contract or a fallback surface. This is a conditional capability-honesty risk rather than a claim that the working Center never exposes extra actions.

   Accessibility needs implementation, not just more screenshots: the [host verification document](notification-center-verification.md#L9) records no semantic-tree bridge in the pinned Iced/layer-shell stack. Action labels are [drawn beside icons](../crates/canopa-notify/src/presentation.rs#L1837), but visible text is not proof of accessible names/roles/states. The [action-icons hint](https://specifications.freedesktop.org/notification/1.3/hints.html) specifically calls for the localized action label as accessibility annotation. Complete the bridge, names, roles, states, image alternatives, and update announcements, then verify them with assistive technology. Do not report this as a completed advertised-surface acceptance pass.

2. **Finish static-image and body-image acceptance before advertising `body-images`.** Local body images are already decoded and rendered; [bounded preparation](adr/0036-bounded-banner-image-preparation.md) and [body widgets](../crates/canopa-notify/src/presentation.rs#L1969) are implemented. Remaining work is the cross-surface/host acceptance gate, asset fallbacks and supported-scale/theme coverage, including the documented format limitations. The [image specification](https://specifications.freedesktop.org/notification/1.3/icons-and-images.html) supplies raw-layout, source-priority, and local-file/theme-reference rules. It does not make every optional visual feature mandatory. XPM/SVG and automatic desktop-theme/output-scale tracking remain explicitly open in W09; distinguish the selected PNG/JPEG subset from complete support for other referenced standards.

3. **Implement safe hyperlinks end to end (W12).** Targets currently are not retained as actionable links, and `body-hyperlinks` is correctly absent. Preserve link targets, define allowed URI handling, render meaningful link affordances and activation on banners/Center, cover replacement and fallback behavior, and pass host verification before advertising. The [markup specification](https://specifications.freedesktop.org/notification/1.3/markup.html) distinguishes links from notification actions and does not require a browser-like implementation.

4. **Define and implement persistence (W13), or explicitly narrow the release scope.** Durable local history already exists, but expiration, stale entries, acknowledgement, retention/pruning, sender recall, and transient behavior need one documented sender-visible contract plus tests. Closed historical records alone do not establish the [persistence capability](https://specifications.freedesktop.org/notification/1.3/protocol.html). The approved plan permits excluding persistence from a release only with an explicit narrower completion claim.

5. **Close operational and failure acceptance, then package a reproducible release (W02/W05/W06/W07/W14).** The tracker still lists abrupt-import/upgrade interruption, storage/backfill-scale cases, signal/renderer failure and shutdown draining, aggregate projection/query/diagnostic resource work, and graphical restart recovery. Finish the supported output/font/locale and host acceptance matrix; document supported recovery behavior. Complete clean-checkout build/test/install/configure/upgrade/remove guidance and release checks. These are product completion and reliability gates; the specification does not prescribe a particular restart architecture, database, resource budget, or documentation layout.

## Scope cautions

Critical notifications do not expire by default. The [urgency chapter](https://specifications.freedesktop.org/notification/1.3/urgency-levels.html) recommends no automatic critical expiry; the approved plan explicitly leaves positive sender timeouts as a documented policy choice. Do not turn that SHOULD-level tension into an unqualified mandatory-protocol failure.

Likewise, authenticated application identity, native portal v2, animation, and honoring sender coordinates on Wayland need separate scope decisions. The [capability/hint matrix](freedesktop-notification-compliance.md) already distinguishes optional support and compatibility extensions. The unnamespaced `activation-token` capability is a documented interoperability extension; the standard signal and the extension advertisement are separate facts.

No new unequivocal core wire-contract defect was established in this focused review. The strongest reasons not to call the selected project target complete are the unfinished accessible/all-action presentation contract, incomplete image acceptance, pending links and persistence, and remaining operational/release acceptance.
