# Revision-bound Notification Center actions

Notification Center controls refer to the content displayed when they were built, not whatever revision happens to exist when a queued click reaches the daemon. Extending ADR 0030's banner policy to this external surface, each Notification Center Target captures the thread ID, revision and a fresh random daemon-instance identifier; replacement, termination or a new daemon lifetime invalidates it before any sender-visible effect. Instance identity matters because runtime-only transient IDs and revisions can recur after restart. Ordinary CLI/current-state commands retain their existing semantics.

The runtime derives targets with the projection and reuses the existing revision-checked activation/action commit path, including revalidation after activation-token acquisition outside the mutation coordinator. Targets are not authorization credentials and require no persisted state or growing registry. The provider carries the typed center command in each generic action's opaque value and verifies its item ID and action kind when decoding. Missing/legacy unguarded item-action values fail closed; deploy daemon and provider together. Stable panel item IDs and the Canopa-v3 protocol are unchanged, so the generic Niribar host needs no port for this change. This supersedes the earlier W04 ticket comment that treated center clicks as current-state commands; it does not change bulk clear, permissions, D-Bus signatures, capability advertising or host focus policy.
