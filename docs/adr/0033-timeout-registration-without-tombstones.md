# Timeout registration without lifetime tombstones

The Notification Runtime owns one timeout record per registered live revision, transitioning from pending display to a scheduled task. Only committed lifecycle effects applied in mutation order can register records; display acknowledgements carry captured IDs/revisions and may start an existing pending record, never insert or reconstruct one. Registration, cancellation and scheduling share one lock, so closure or replacement can reclaim the old record immediately without a permanent cancellation tombstone or a check-then-schedule race.

Timeout duration remains lifecycle-owned and resolves on first display, preserving ADR 0028. Duplicate/late acknowledgements do nothing after scheduling, cancellation or completion. A firing task removes its own matching record before awaiting lifecycle expiration; this prevents terminal-effect cleanup from aborting its own committed-effect publication. Failed receipt or user/sender transition writes leave existing registrations unchanged, while partial clear applies only committed cancellations. A firing task consumes its registration even if expiry storage fails; this preserves the existing no-retry behavior rather than adding recovery here. The registration count is bounded by the live admission limit in ADR 0032 and returns to zero after completed churn; this is not a bound on all process memory, external presenters holding callbacks, or unrelated workers. Control status exposes `timeout_records` as content-free operational evidence.
