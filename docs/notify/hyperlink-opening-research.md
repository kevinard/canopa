# Opening notification hyperlinks

Research date: 2026-09-16. Scope: activating explicitly selected HTTP/HTTPS body links from Notify and Niribar, using a small Rust adapter; an additional inventory checks whether Orca acceptance can run with the current machine's files. This is an implementation recommendation, not completed graphical acceptance.

## Recommended desktop interface

Use `org.freedesktop.portal.OpenURI.OpenURI` on service `org.freedesktop.portal.Desktop`, object `/org/freedesktop/portal/desktop`. The method takes `(parent_window: s, uri: s, options: a{sv})` and returns a Request object path. Relevant options are `handle_token`, `ask` (since interface version 3), and `activation_token` (since version 4). Omit `ask` for normal default-browser behavior. The API supports URIs generally but excludes `file://`; Notify should impose its own HTTP/HTTPS policy. Version 5 also has `SchemeSupported`, which is unnecessary when supporting older portal versions. [OpenURI API](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.OpenURI.html)

Pass an empty `parent_window` unless the renderer has a genuine exported window handle. A Wayland parent identifier contains an `xdg_foreign` handle; an Iced window ID, Wayland object ID, or notification ID is not such a handle. The protocol explicitly allows the empty string when no suitable handle exists. [Window identifiers](https://flatpak.github.io/xdg-desktop-portal/docs/window-identifiers.html)

The method's successful reply means that a request exists. Actual completion arrives in `org.freedesktop.portal.Request.Response(response: u, results: a{sv})`: 0 means success, 1 user cancellation, and 2 another termination. `Request.Close()` ends the interaction and does **not** subsequently emit `Response`. The predictable handle is `/org/freedesktop/portal/desktop/request/SENDER/TOKEN`, with the caller's leading colon removed and periods converted to underscores. Supply a unique unpredictable valid object-path element as `handle_token`, using a library prefix and random bytes. Subscribe before sending `OpenURI` to avoid missing an immediate response. The returned handle must be checked because older services can choose a different one. [Request API](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.Request.html)

GLib's `Gio.AppInfo.launch_default_for_uri_async` is another maintained desktop opening API; it accepts a launch context and cancellation object. The installed `gio open` command exposes default-handler opening without adding GLib bindings to Notify. `xdg-open` also delegates HTTP/HTTPS to the preferred browser, with exit status indicating launcher success/failure. Neither command's successful exit establishes that a remote page loaded. [GIO API](https://docs.gtk.org/gio/type_func.AppInfo.launch_default_for_uri_async.html), [xdg-open manual](https://portland.freedesktop.org/doc/xdg-open.html)

Recommendation: implement the portal adapter first because it fits the existing zbus/Tokio dependencies and represents cancellation explicitly. If a CLI fallback is desired for desktops without a portal, use `gio open` or `xdg-open` only after a definitive pre-submission unavailability result. Invoke it with separate process arguments, never a shell command containing the URI. Do not fallback after a portal cancellation, rejection, timeout, or uncertain transport result: the original request may already have launched, or the user may have declined it. This fallback policy is a project design recommendation.

## Activation and revision boundaries

Wayland activation tokens should come from the user's actual click/keyboard context. The protocol's optional `set_app_id` identifies the **application being activated**, while `set_surface` identifies the requesting surface; an event serial can authorize the transfer. A token may be ineffective and the requester cannot reliably determine its validity. Supplying a token requests activation rather than guaranteeing focus. These facts were checked against the installed official protocol XML at `/usr/share/wayland-protocols/staging/xdg-activation/xdg-activation-v1.xml`. [Upstream protocol source](https://gitlab.freedesktop.org/wayland/wayland-protocols/-/blob/main/staging/xdg-activation/xdg-activation-v1.xml)

Local-source observation: Notify's existing `activation_token_task` and the vendor `request_activation_token` preserve source seat, serial, and surface, but always supply an `app_id`. A body hyperlink usually does not know which browser the portal will choose. Extend that seam to omit `set_app_id` for unknown targets; do not reuse the notification sender's app identity as the browser target. Include a nonempty token in portal options only when its interface version supports it. For a direct child-process fallback, the Wayland protocol defines `XDG_ACTIVATION_TOKEN` as a transfer mechanism; give it only to that process rather than changing the daemon environment.

The following application policy is recommended:

- Parse links during body interpretation, preserving visible text and the target separately. Permit only absolute HTTP/HTTPS URLs with a host. Reject literal control characters before parsing because URL parsers may normalize them. Consider rejecting credentials to avoid misleading user-information prefixes. Keep existing notification size limits; add a bounded target length if the rich-body model needs one.
- Resolve a user's activation through a revision-scoped link identity, never a target supplied directly by a panel event. Recheck the current revision after waiting for an activation token and immediately before submitting the opener call. Replacements must not retarget an already queued click.
- Opening a body link is not a freedesktop sender action. It should not synthesize `ActionInvoked` or automatically dismiss the notification unless the documented product policy explicitly requires that behavior.
- After submission, retain the original validated target. Arrival of a new notification should not silently replace the user's pending browser request. Report opening failures through the existing user-visible/error path without logging full notification URLs unnecessarily.

The cached `url` crate is 2.5.8 and already appears transitively in `Cargo.lock`; it can become a direct dependency for validation. No `ashpd` source was found in the Cargo cache. A separate portal convenience dependency is unnecessary for the small interface described here.

## Small testable zbus adapter

Use a domain-facing trait whose input is a validated URL plus optional activation token and whose result distinguishes `Opened`, `Cancelled`, `Unavailable`, `Failed`, and `TimedOut`. Inject it into the runtime in the same style as the activation-token provider. Keep portal details out of body parsing and panel protocol types. The adapter owns the D-Bus request through its terminal result; tests inject a connection to a private bus and a short deadline.

Suggested operation, with bounded concurrent requests:

1. Obtain a session connection and the portal interface version. Resolve the service's unique bus owner after activation. Pin the method destination and signal sender to that owner for this request, so a service restart cannot substitute a different producer midway through the call.
2. Generate `handle_token` using the existing `rustix::rand` facility. Derive the expected request path from `connection.unique_name()`.
3. Register a signal stream **before** calling the method. One straightforward implementation uses `MessageStream::for_match_rule` for `Signal`, the resolved unique sender, interface `org.freedesktop.portal.Request`, member `Response`, and the request path namespace. Start consuming promptly and filter by the actual returned handle. A namespace subscription captures an early response even if a legacy portal returns an unexpected path. The signal queue and number of in-flight requests should be bounded together.
4. Call `OpenURI` with `HashMap<&str, zbus::zvariant::Value<'_>>` options and deserialize its result as `OwnedObjectPath`. Deserialize the matching response as `(u32, HashMap<String, OwnedValue>)`. Reject malformed messages and unknown response codes.
5. On the chosen response deadline or explicit shutdown cancellation, best-effort `Close()` on the same owner's returned request path, with a short separate cleanup deadline. Await its method reply, but do not wait for a `Request.Response` signal afterward. Release the stream/match rule after completion.

Local zbus 5.14.0 and 5.16.0 sources document that `MessageStream` must be consumed continuously; retaining an unpolled stream can stall message delivery. They also document that raw `MatchRule::matches` cannot verify a well-known sender name against an incoming unique sender, so use a **resolved unique owner** for a manually built stream. `Proxy::receive_signal` provides owner tracking for a fixed-path alternative. These details were verified in the cached published sources. [MessageStream source](https://docs.rs/crate/zbus/5.14.0/source/src/message_stream.rs), [MatchRule source](https://docs.rs/crate/zbus/5.14.0/source/src/match_rule/mod.rs), [Proxy source](https://docs.rs/crate/zbus/5.14.0/source/src/proxy/mod.rs)

Timeouts are application policy, not a portal-specified constant. Use a bounded method-call setup timeout and a much longer response deadline that accommodates a person choosing an application; two minutes is a reasonable initial response policy, not a protocol requirement. A dropped Rust method future does not retract an already sent D-Bus call. If setup times out before a handle is returned, classify the outcome as uncertain, attempt cleanup on the predicted handle, and do not retry through another opener. Ensure task cancellation still runs request cleanup; an async future simply being dropped is not sufficient.

Private-bus tests should cover: response sent before the method reply; alternate returned handle; success; cancellation; failure; malformed response; wrong sender/path; absent service; missing optional version support; timeout calls `Close`; `Close` produces no response; service disappearance; token forwarding; replacement while awaiting a token; and no duplicate launch after any uncertain outcome. Test through actual zbus messages, not only a mock function that returns a successful enum.

## Graphical acceptance

Observed installed components: xdg-desktop-portal 1.22.0, xdg-desktop-portal-gtk 1.15.3, Niri 26.04, Sway 1.12, GTK3, `gio`, and xdg-open 1.2.1. A read-only query of the live desktop returned **OpenURI version 5**. The GTK portal advertises the AppChooser backend needed by the frontend. No URL was opened during this research.

For repeatable graphical acceptance, run a nested supported compositor with a private session bus and fresh XDG runtime/config/data directories. Start the real portal frontend and GTK backend in that environment. Provide fixture-local `portals.conf` selecting GTK and a fixture-local default HTTP/HTTPS handler desktop file. The handler should open a small real window, record the exact URI and received activation token, and then exit cleanly. Test normal default opening and chooser cancellation through actual Notify/Niribar controls. The desktop association and backend overrides belong only to the fixture. [Portal backend selection](https://flatpak.github.io/xdg-desktop-portal/docs/portals.conf.html), [default application associations](https://specifications.freedesktop.org/mime-apps/latest/default.html)

Verify mouse, keyboard, and AT-SPI activation; long labels; ordered links between text/images; same-ID replacement; expired or cleared content; mixed scale; and both banner and Center. The recorder establishes exact dispatch without contacting external sites. A final browser run against a fixture-local HTTP server can establish actual page navigation and compositor activation without depending on the internet. Cancellation must leave the page unopened and the notification usable.

## Can Orca run with the current files?

Not immediately. Read-only inventory found no Orca executable, Python package, local source checkout, or cached Orca package. `speech-dispatcher` and Python `speechd` are absent. Python `dasbus`, required by Orca 50.2, is also absent. Installed foundations include Python 3.14, PyGObject, Cairo, GTK3, AT-SPI 2.60.4, dconf, GSettings schemas, psutil, Meson, and Ninja. Optional Wnck, BrlAPI, Liblouis Python bindings, and setproctitle are absent. The package-manager's existing repository metadata lists Orca 50.2-1 and speech-dispatcher 0.12.1-3; it is metadata, not an installed runtime.

Orca 50.2's official build requires Python >=3.10, AT-SPI/ATK bridge >=2.56, PyGObject, GTK3 >=3.24, and `dasbus`. Speech Dispatcher, braille modules, and Wnck are optional at build time. Thus a source build under `/tmp` with downloaded Orca and dasbus is a plausible route to real Orca event-handling tests without system installation. Audible speech additionally needs a speech provider and synthesizer. This is a dependency-based inference; no source build or Orca run was performed here. [Orca 50.2 build requirements](https://github.com/GNOME/orca/blob/50.2/meson.build)

Pin the 50.2 release for that fixture and use its documented alternate Meson prefix; avoid moving `main`, whose newer development dependencies differ. Run it on the existing isolated AT-SPI fixture with the nested compositor. Set separate configuration and schema paths, use fixture-owned preferences, and capture a debug file. Starting with Orca 50, settings use GSettings, so the old user-prefs directory option alone should not be assumed to isolate all preferences. Disabling speech can exercise events but does not establish spoken usability. [Orca 50.2 build/configuration documentation](https://github.com/GNOME/orca/blob/50.2/README.md), [application-developer guidance](https://github.com/GNOME/orca/blob/50.2/README-APPLICATION-DEVELOPERS.md)
