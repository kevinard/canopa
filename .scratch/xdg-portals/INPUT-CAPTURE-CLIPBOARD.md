## InputCapture v2: exact backend surface

Both pinned public and backend InputCapture XML describe **version 2**. The frontend advertises `min(max(impl.version, 1), 2)` and binds `SupportedCapabilities` from the backend. Capabilities are a constant implementation mask: keyboard `1`, pointer `2`, touchscreen `4`; granted session capabilities must be a subset of those requested. This mask is not current device availability. [Backend XML:31, 160–171, 504–520](/tmp/canopa-xdp-session-canonical-13/xdg-desktop-portal-1.22.1/data/org.freedesktop.impl.portal.InputCapture.xml:31), [frontend C:1653–1660](/tmp/canopa-xdp-session-canonical-13/xdg-desktop-portal-1.22.1/src/input-capture.c:1653).

All methods below are on `org.freedesktop.impl.portal.InputCapture`. In this table, `D = a{sv}`, `o = object path`, `s = string`, `u = uint32`, `h = Unix FD handle`. These are backend signatures, not the public asynchronous Request signatures.

| Method | Inputs → outputs | Required semantics |
| --- | --- | --- |
| `CreateSession` (deprecated) | `handle:o, session_handle:o, app_id:s, parent_window:s, options:D → response:u, results:D` | Version 1 form creates an already-started session; requests `capabilities:u`. |
| `CreateSession2` | `session_handle:o, app_id:s, options:D → results:D` | Version 2 creates an unstarted session. No supported options/result keys. It has no request handle and no numeric portal response output. |
| `Start` | `handle:o, session_handle:o, app_id:s, parent_window:s, options:D → response:u, results:D` | Once per v2 session; consent and grant. Required nonzero `capabilities:u`; optional `restore_data:(suv)`, `persist_mode:u`. Results include `capabilities:u`, optionally `clipboard_enabled:b`, `restore_data:(suv)`. |
| `GetZones` | `handle:o, session_handle:o, app_id:s, options:D → response:u, results:D` | Results `zones:a(uuii)`, `zone_set:u`. Each zone is width, height, x, y. |
| `SetPointerBarriers` | `handle:o, session_handle:o, app_id:s, options:D, barriers:aa{sv}, zone_set:u → response:u, results:D` | Each barrier has nonzero `barrier_id:u`, `position:(iiii)`; return `failed_barriers:au`. |
| `Enable`, `Disable`, `Release` | each `session_handle:o, app_id:s, options:D → response:u, results:D` | These backend calls still have two outputs although their public counterparts return no values. `Release` options contain `activation_id:u` and optional suggested `cursor_position:(dd)`. |
| `ConnectToEIS` | `session_handle:o, app_id:s, options:D → fd:h` | Backend returns the connected socket FD to the frontend, which passes it to the application. No portal-response tuple. |

Signature sources: [CreateSession/CreateSession2:68–103](/tmp/canopa-xdp-session-canonical-13/xdg-desktop-portal-1.22.1/data/org.freedesktop.impl.portal.InputCapture.xml:68), [Start:105–200](/tmp/canopa-xdp-session-canonical-13/xdg-desktop-portal-1.22.1/data/org.freedesktop.impl.portal.InputCapture.xml:105), [GetZones/barriers:202–281](/tmp/canopa-xdp-session-canonical-13/xdg-desktop-portal-1.22.1/data/org.freedesktop.impl.portal.InputCapture.xml:202), [Enable/Disable/Release/ConnectToEIS:283–375](/tmp/canopa-xdp-session-canonical-13/xdg-desktop-portal-1.22.1/data/org.freedesktop.impl.portal.InputCapture.xml:283).

Backend signals are `Disabled(session_handle:o, options:D)`, `Activated(o,D)`, `Deactivated(o,D)` and `ZonesChanged(o,D)`. Properties are `SupportedCapabilities:u` and lowercase `version:u`. Activation options use `activation_id:u`, `cursor_position:(dd)`, and optional `barrier_id:u`; deactivation uses the corresponding activation ID and may carry cursor position. [Backend XML:377–520](/tmp/canopa-xdp-session-canonical-13/xdg-desktop-portal-1.22.1/data/org.freedesktop.impl.portal.InputCapture.xml:377).

### Frontend v2 translation is material

The public v2 `CreateSession2(options:D) → results:D` returns a `session_handle:o` inserted by the frontend. The backend's `CreateSession2` result dictionary itself has no supported keys. Public `Start(session_handle:o, parent_window:s, options:D) → handle:o` completes later via the public Request response signal. A backend must therefore not implement the public signatures under the impl interface. [Public XML:122–260](/tmp/canopa-xdp-session-canonical-13/xdg-desktop-portal-1.22.1/data/org.freedesktop.portal.InputCapture.xml:122), [frontend C:413–439, 724–734](/tmp/canopa-xdp-session-canonical-13/xdg-desktop-portal-1.22.1/src/input-capture.c:413).

**A public legacy `CreateSession` call still reaches the backend v2 path.** When the backend advertises v2, pinned frontend `handle_create_session` synchronously calls backend `CreateSession2`, then asynchronously backend `Start`, passing the old public CreateSession capabilities/parent window into Start. It does not call deprecated backend CreateSession. Advertising v2 while implementing only the deprecated method would fail both old and new public clients. [Frontend C:319–358](/tmp/canopa-xdp-session-canonical-13/xdg-desktop-portal-1.22.1/src/input-capture.c:319).

The frontend owns public request/session paths, original application attribution, option filtering and restore-token storage/translation. Backend `Start` receives implementation-private `restore_data`, never the public restore token. Canopa owns consent, grant subset, private restore format and whether permissions may persist. A first implementation can decline persistence and require consent each time; that is a proposed policy, not evidence of existing InputCapture support. [Frontend C:614–618, 642–734](/tmp/canopa-xdp-session-canonical-13/xdg-desktop-portal-1.22.1/src/input-capture.c:614), [backend XML:129–186](/tmp/canopa-xdp-session-canonical-13/xdg-desktop-portal-1.22.1/data/org.freedesktop.impl.portal.InputCapture.xml:129).

### Capture state, zones, barriers and EI direction

The public contract distinguishes **enabled** from **active**. Only the compositor decides when capture activates and which approved devices it captures. Active events go to the application instead of ordinary on-screen pointer handling. There is no application method to force immediate activation. The portal manages consent/state; EI carries events. [Public XML:28–54](/tmp/canopa-xdp-session-canonical-13/xdg-desktop-portal-1.22.1/data/org.freedesktop.portal.InputCapture.xml:28).

The useful state sequence is: create unstarted → Start consent → started → ConnectToEIS → disabled/connected → Enable → enabled → compositor trigger → active → Release or compositor deactivation → enabled. Disable returns to disabled; Close is terminal. The pinned frontend allows GetZones/barrier setup after Start, permits ConnectToEIS only in started state, rejects a second connection, and requires connection before Enable/Disable/Release. The same EI connection survives Disable/Enable until session closure. [Frontend C:837–851, 1102–1121, 1412–1449](/tmp/canopa-xdp-session-canonical-13/xdg-desktop-portal-1.22.1/src/input-capture.c:837), [public XML:498–509](/tmp/canopa-xdp-session-canonical-13/xdg-desktop-portal-1.22.1/data/org.freedesktop.portal.InputCapture.xml:498).

Zone sets are session-specific logical rectangles and may be discontinuous or empty. `zone_set` increases with topology changes and must support wrapping. Barriers must be horizontal or vertical, lie on the outside boundary of the union of zones, and be fully contained by one zone. Spans are pixel-inclusive: x=0 through x=1 covers two pixels; the right/bottom boundary can be at the zone's offset plus width/height. A crossing is tested against the logical motion before clipping, so an activation cursor position may lie outside all zones. Empty barriers remove all barriers; replacing barriers suspends capture and requires another Enable. Stale zone sets must fail barrier setup. [Public XML:268–367](/tmp/canopa-xdp-session-canonical-13/xdg-desktop-portal-1.22.1/data/org.freedesktop.portal.InputCapture.xml:268).

`ZonesChanged.options.zone_set` identifies the **invalidated** zone set, not the new one. Applications re-read zones and establish barriers again. The backend XML's shorter ZonesChanged description omits that option; the public XML provides the more precise contract. [Public XML:626–651](/tmp/canopa-xdp-session-canonical-13/xdg-desktop-portal-1.22.1/data/org.freedesktop.portal.InputCapture.xml:626), [backend XML:489–502](/tmp/canopa-xdp-session-canonical-13/xdg-desktop-portal-1.22.1/data/org.freedesktop.impl.portal.InputCapture.xml:489).

Activation IDs increase with wrapping and synchronize portal `Activated` with EI `start_emulating.sequence`: the same ID precedes the first captured device event. Deactivated refers to the corresponding activation. A stale Release must not stop a newer activation. Its cursor position is a suggestion, not a required warp. Compositor-triggered disable while active emits Deactivated before Disabled. Public caller-driven Disable/Release do not promise matching public signals; delayed earlier signals can still arrive. [Backend XML:325–341, 377–447](/tmp/canopa-xdp-session-canonical-13/xdg-desktop-portal-1.22.1/data/org.freedesktop.impl.portal.InputCapture.xml:325), [public XML:425–489](/tmp/canopa-xdp-session-canonical-13/xdg-desktop-portal-1.22.1/data/org.freedesktop.portal.InputCapture.xml:425).

**InputCapture is compositor/EIS → application EI receiver. RemoteDesktop is application EI sender → compositor injection.** The returned `h` is a connected Unix socket passed through D-Bus FD passing, not an integer OS descriptor embedded without an FD list. The app uses a receiver/passive EI context. Canopa's existing EIS worker explicitly requires `ContextType::Sender` and rejects a receiver, so it is not an InputCapture implementation. Rust `reis` already has receiver-side server helpers (`start_emulating`, `stop_emulating`, `frame`) and a receiver example; this is library capability only, not a capture service. [Backend XML:354–375](/tmp/canopa-xdp-session-canonical-13/xdg-desktop-portal-1.22.1/data/org.freedesktop.impl.portal.InputCapture.xml:354), [current worker:190–204](/home/kevinard/projects/canopa/crates/canopa-portal/src/remote_input/server.rs:190), [reis:1136–1168](/home/kevinard/projects/canopa/vendor/reis/src/request.rs:1136), [reis example:121–131](/home/kevinard/projects/canopa/vendor/reis/examples/reis-demo-server.rs:121). The official [EI API](https://libinput.pages.freedesktop.org/libei/api/group__libei.html) distinguishes sender and receiver contexts; [EIS documentation](https://libinput.pages.freedesktop.org/libei/api/group__libeis.html) distinguishes their server-side APIs.

### Do not delegate backend correctness to the frontend

The inspected frontend forwards `barriers` and `zone_set` with explicit validation FIXME comments. It forwards GetZones/barrier results without validating geometry. A nonzero GetZones/barrier response or a cancelled request closes the public session; ordinary per-barrier rejection should therefore use a successful response plus `failed_barriers`, rather than indiscriminately returning a fatal portal response. [Frontend C:770–789, 931–949, 1046–1055](/tmp/canopa-xdp-session-canonical-13/xdg-desktop-portal-1.22.1/src/input-capture.c:770).

Enable/Disable/Release are forwarded asynchronously without observing backend completion; a public successful method return does not prove compositor action. The backend must enforce its own state and revoke on transport failure. Two pinned implementation details deserve explicit compatibility tests: Enable unconditionally assigns frontend ENABLED before its leniency switch, including after an ACTIVE state; ConnectToEIS sets frontend DISABLED even in its logged backend-failure branch. These are inspected behaviors, not desired state-machine rules, and this investigation does not change them. [Frontend C:1132–1160, 1254–1262, 1359–1367, 1433–1449](/tmp/canopa-xdp-session-canonical-13/xdg-desktop-portal-1.22.1/src/input-capture.c:1132).

## Clipboard v1: authorization and transfer lifetime

Clipboard public XML describes **version 1** and frontend C always exports version 1. Clipboard does not create sessions: it extends RemoteDesktop or InputCapture sessions. A successful RequestClipboard means the request was recorded, not that access was granted. Consent is decided at the owning portal's Start and reported as `clipboard_enabled:b`. [Public XML:24–51](/tmp/canopa-xdp-session-canonical-13/xdg-desktop-portal-1.22.1/data/org.freedesktop.portal.Clipboard.xml:24), [frontend C:119–164, 621](/tmp/canopa-xdp-session-canonical-13/xdg-desktop-portal-1.22.1/src/clipboard.c:119).

All methods below are on `org.freedesktop.impl.portal.Clipboard`. Unlike InputCapture, **none includes app_id or a request handle**; ownership must come from the existing session and the authenticated D-Bus sender.

| Method/signal | Exact signature | Meaning |
| --- | --- | --- |
| `RequestClipboard` | `session_handle:o, options:a{sv} → ()` | Before session Start; record desire for clipboard consent. |
| `SetSelection` | `session_handle:o, options:a{sv} → ()` | Advertise formats as `mime_types:as`, making this session the source. |
| `SelectionWrite` | `session_handle:o, serial:u → fd:h` | Backend creates/returns writable FD to the application answering an earlier transfer request. |
| `SelectionWriteDone` | `session_handle:o, serial:u, success:b → ()` | Complete/fail that requested transfer. |
| `SelectionRead` | `session_handle:o, mime_type:s → fd:h` | Backend creates/returns readable FD carrying local clipboard content. |
| `SelectionOwnerChanged` signal | `session_handle:o, options:a{sv}` | Options `mime_types:as`, `session_is_owner:b`. |
| `SelectionTransfer` signal | `session_handle:o, mime_type:s, serial:u` | Request bytes from a session-owned selection; the backend issues the serial. |
| Property | `version:u` (read-only) | Version 1. |

Sources: [backend XML:31–180](/tmp/canopa-xdp-session-canonical-13/xdg-desktop-portal-1.22.1/data/org.freedesktop.impl.portal.Clipboard.xml:31), [public XML:83–179](/tmp/canopa-xdp-session-canonical-13/xdg-desktop-portal-1.22.1/data/org.freedesktop.portal.Clipboard.xml:83). Both SelectionRead and SelectionWrite return FDs **outward** from the callee. SelectionWrite does not take an incoming app-created FD. The frontend copies backend FD handles into a new outgoing Unix FD list for the original caller. [Frontend C:254–287, 407–437](/tmp/canopa-xdp-session-canonical-13/xdg-desktop-portal-1.22.1/src/clipboard.c:254).

RequestClipboard is allowed only once before Start and requires owning backend version ≥2 for both supported session types. For InputCapture it requires INIT; SetSelection/SelectionRead require granted clipboard plus ACTIVE capture. For RemoteDesktop the frontend access predicate is simply `clipboard_enabled`, which is set from Start. Clipboard never independently authorizes a ScreenCast-only session. [Clipboard frontend:63–111](/tmp/canopa-xdp-session-canonical-13/xdg-desktop-portal-1.22.1/src/clipboard.c:63), [InputCapture frontend:187–226](/tmp/canopa-xdp-session-canonical-13/xdg-desktop-portal-1.22.1/src/input-capture.c:187), [RemoteDesktop frontend:171–214](/tmp/canopa-xdp-session-canonical-13/xdg-desktop-portal-1.22.1/src/remote-desktop.c:171).

Transfer flow when the application owns the selection:

1. Application calls SetSelection with MIME types; this advertises availability, not eager bytes.
2. A local consumer requests a MIME type. Backend emits SelectionTransfer with a serial bound to this session and source offer.
3. Application calls SelectionWrite with that serial, writes bytes to the returned writable FD, closes it, then calls SelectionWriteDone(success). A declined/unhandled request must report false.
4. Backend retires the transfer and its descriptors on completion, failure, cancellation or bounded expiry. A serial is not authority to read a different selection/session.

The first three steps follow [backend XML:57–170](/tmp/canopa-xdp-session-canonical-13/xdg-desktop-portal-1.22.1/data/org.freedesktop.impl.portal.Clipboard.xml:57); bounded expiry and an offer-bound ledger in step four are proposed Rust enforcement choices. XML defines completion reporting but does not specify a universal timeout or a complete in-flight cancellation policy.

**New access and completion are distinct.** Pinned frontend checks current access for SetSelection and SelectionRead, but SelectionWrite/SelectionWriteDone check the grant and session identity without checking InputCapture ACTIVE. Signal forwarding also checks only grant plus not-closed, not ACTIVE. Thus the frontend does not prevent a backend from leaking new owner-change information while inactive, nor does it define the backend's lifetime of outstanding serials. Canopa must suppress new reads/ownership changes/transfer creation outside the permitted phase, and deliberately decide whether an already-admitted transfer drains or is cancelled on deactivation. It must not accidentally accept an arbitrary serial merely because clipboard consent once existed. [Frontend C:202–218, 301–337, 353–389, 472–488, 544–608](/tmp/canopa-xdp-session-canonical-13/xdg-desktop-portal-1.22.1/src/clipboard.c:202).

As an implementation reference only, current official Mutter source keeps transfer requests keyed by serial, uses a 15-second unanswered-request cleanup, creates a pipe and returns its write end for SelectionWrite, and clears current source/pending transfers/read work when clipboard access is disabled. These are reference policies, not additional 1.22.1 portal guarantees. [Mutter meta-clipboard-session.c, cleanup/disable/write](https://github.com/GNOME/mutter/blob/main/src/backends/meta-clipboard-session.c#L31).

File data should follow `application/vnd.portal.filetransfer` and the separate frontend FileTransfer portal rather than inventing a Canopa URI or sandbox-file grant path. This is a contract boundary, not a claim that Canopa already implements file clipboard bridging. [Backend XML:64–65](/tmp/canopa-xdp-session-canonical-13/xdg-desktop-portal-1.22.1/data/org.freedesktop.impl.portal.Clipboard.xml:64).

## Ownership and teardown shared by both interfaces

The frontend authenticates the **original app's unique bus sender and app_id** for public session use; it creates the public session path and closes on original app disconnect. The backend normally sees the frontend as its D-Bus caller, not that original app. Therefore retain the frontend's unique owner, app identity and session kind at backend creation; Clipboard's app-id-free methods must use that stored identity, not infer trust from a path string or PID. [XDP xdp-session.c:69–113, 355–387](/tmp/canopa-xdp-session-canonical-13/xdg-desktop-portal-1.22.1/src/xdp-session.c:69), [Canopa session creation:46–133](/home/kevinard/projects/canopa/crates/canopa-portal/src/screencast/session.rs:46), [Canopa lookup:214–232](/home/kevinard/projects/canopa/crates/canopa-portal/src/screencast.rs:214).

Canopa already exports an impl Session endpoint checking the stored caller for Close, watches that caller before checking its existence, owns bounded command/session slots, and retires resources before removing the endpoint. These are reusable lifetime patterns. Its current host has Capture/Remote kinds and Configuring/Starting/Active phases; InputCapture's started/connected/enabled/capturing distinction does not already exist there. Clipboard is currently explicitly false in RemoteDesktop results. [Session actor:6–24, 26–43, 67–133, 136–175, 188–218, 467–509](/home/kevinard/projects/canopa/crates/canopa-portal/src/screencast/session.rs:6), [RemoteDesktop results:469–493](/home/kevinard/projects/canopa/crates/canopa-portal/src/screencast/remote.rs:469).

Canonical XDP pins impl Session cleanup to the original backend unique owner, latches well-known-name loss/replacement, rejects stale sessions, and sends bounded no-autostart cleanup to the displaced original. This companion also matters for the new session kinds, but it does not replace backend teardown when its frontend disappears. No session should silently reconnect to replacement frontend/compositor owners or survive an owner-loss/reacquisition interval. [Canonical xdp-session.c:144–155, 288–350, 442–483](/tmp/canopa-xdp-session-canonical-13/xdg-desktop-portal-1.22.1/src/xdp-session.c:144). The existing remote worker subscribes before identity validation and pins compositor unique owner/PID/socket credentials; reuse the principle, not its injection semantics. [remote_input.rs:97–153](/home/kevinard/projects/canopa/crates/canopa-portal/src/remote_input.rs:97).

## Inspected Niri capability boundary

### InputCapture gap: compositor work is required

The inspected Niri D-Bus module exposes the private RemoteInput injection service and other desktop services; RemoteInput methods open keyboard, pointer and mapped-pointer **command** leases. The input event dispatcher routes keyboard/motion/buttons/axis to normal handling, and pointer motion computes a new on-screen location before pointer-constraint handling. Searching its source/IPC tree found no InputCapture session service, capture barriers, portal zones/activation state, or EI receiver producer. This supports a concrete gap in this prepared tree: it has input injection, not compositor-owned input capture. [Niri D-Bus registrations:11–24, 97–107](/home/kevinard/projects/canopa/target/niri-pointer-stage-01/niri-b22eb842ca9506d4e2ff997b116031cdb3f650f8/src/dbus/mod.rs:11), [RemoteInput:130–218](/home/kevinard/projects/canopa/target/niri-pointer-stage-01/niri-b22eb842ca9506d4e2ff997b116031cdb3f650f8/src/dbus/remote_input.rs:130), [input dispatcher:191–220](/home/kevinard/projects/canopa/target/niri-pointer-stage-01/niri-b22eb842ca9506d4e2ff997b116031cdb3f650f8/src/input/mod.rs:191), [pointer path:2688–2722](/home/kevinard/projects/canopa/target/niri-pointer-stage-01/niri-b22eb842ca9506d4e2ff997b116031cdb3f650f8/src/input/mod.rs:2688).

Inference: an Iced window, ordinary Wayland event subscription, pointer lock or existing injection lease cannot provide the specified capture guarantee. The compositor must own crossing detection before clipping, divert approved input from normal focus handling while active, keep escape/revocation working, and publish coherent activation/topology events. A separate privileged capture lease/service is a proposed seam; no such seam is advertised as available today.

### Clipboard transport exists, but it is broad privilege

Niri initializes both `wlr_data_control` and `ext_data_control` with `client_is_unrestricted`. That filter is exactly `!ClientState.restricted`. Ordinary Wayland listener connections are inserted with `restricted:false`; clients admitted through a security-context listener are `restricted:true`. Therefore an unsandboxed Canopa helper using its own ordinary connection to the intended Niri Wayland socket can reach these globals under the inspected policy, while the restricted connection cannot. There is no portal-session permission check in that filter. [Niri filter:2532–2533](/home/kevinard/projects/canopa/target/niri-pointer-stage-01/niri-b22eb842ca9506d4e2ff997b116031cdb3f650f8/src/niri.rs:2532), [globals:2589–2597](/home/kevinard/projects/canopa/target/niri-pointer-stage-01/niri-b22eb842ca9506d4e2ff997b116031cdb3f650f8/src/niri.rs:2589), [ordinary listener:2725–2734](/home/kevinard/projects/canopa/target/niri-pointer-stage-01/niri-b22eb842ca9506d4e2ff997b116031cdb3f650f8/src/niri.rs:2725), [security-context handler:490–500](/home/kevinard/projects/canopa/target/niri-pointer-stage-01/niri-b22eb842ca9506d4e2ff997b116031cdb3f650f8/src/handlers/mod.rs:490).

This is inspected compositor support, not proof of a working Canopa bridge. The data-control protocol provides per-seat selection offers, MIME types and FD-based receive/send. A source is single-use for setting selection; replacing a selection invalidates the old offer, `cancelled` retires a source, `finished` retires the device, and the reader consumes a receive pipe until EOF. These protocol lifetimes still need a Rust mapping to portal session/serial/authorization lifetimes. The portal concerns the regular clipboard; exposing primary selection merely because the transport supports it would need a separate justification. [Official Wayland protocol source](https://gitlab.freedesktop.org/wayland/wayland-protocols/-/blob/main/staging/ext-data-control/ext-data-control-v1.xml), [upstream protocol mirror, requests/events](https://raw.githubusercontent.com/wayland-mirror/wayland-protocols/main/staging/ext-data-control/ext-data-control-v1.xml).

Inference: Clipboard can plausibly start with a Rust data-control adapter without adding a Mutter-compatible Niri Clipboard D-Bus service. Exact owner correlation for `session_is_owner`, echo suppression, cancellation, late requests and revocable transfer pipes remain design and verification work. The current Niri compositor-owned selection callback writes fixed screenshot bytes; it is not a portal transfer broker. ## Proposed implementation seams — not implemented support

1. **A backend session capability shared with Clipboard.** Store frontend unique owner, app_id, kind, requested/granted capabilities, clipboard-requested/granted flags, current capture phase and terminal close state. Keep Capture, RemoteDesktop and InputCapture behavior explicit. Clipboard calls resolve this capability by stored owner; only RemoteDesktop/InputCapture kinds qualify. Reuse Requests for cancellable Start/GetZones/barrier requests and the existing impl Session cleanup pattern. `CreateSession2` needs direct bounded session admission because it has no request handle. Existing [Requests owner/cancel handling](/home/kevinard/projects/canopa/crates/canopa-portal/src/requests.rs:83) and [session actor](/home/kevinard/projects/canopa/crates/canopa-portal/src/screencast/session.rs:188) are starting points, not complete InputCapture state machinery.
2. **A compositor capture lease.** Add a narrow Niri-owned boundary for logical zones/generation, validated barrier replacement, Enable/Disable/Release, capture-event production and terminal revocation. Niri is authoritative for crossing, intercepted events, activation IDs, cursor handback, topology and device loss. The portal owns Iced consent and translates these facts to impl signals. Either Niri serves EI receivers itself or a bounded Rust worker translates a compositor capture transport to `reis`; choose this after proving event ordering and teardown. Do not bolt capture onto the existing EI Sender injection worker by merely allowing its handshake.
3. **Iced consent and controls.** Extend the existing process/presenter pattern with truthful capture direction, selectable supported capabilities, an explicit clipboard choice when requested, and a persistent stop/escape path. The existing [Iced sharing UI](/home/kevinard/projects/canopa/crates/canopa-portal/src/screencast_ui.rs:17) is presentation infrastructure; its current monitor/remote-device choices do not establish InputCapture consent semantics. Unsupported touchscreen capture must remain outside advertised/granted capabilities until implemented and exercised.
4. **A private Rust clipboard transport plus transfer ledger.** Own the seat/data-control connection and source/offer generations. Represent each pending transfer by session, source generation, MIME type, serial, state and owned FDs; consume serials once, reject foreign/replayed/unknown serials and bound simultaneous transfers/metadata/idle duration. Gate new transfers and owner-change signals by session phase. Close/cancel ledger entries on session/frontend/helper/compositor loss, source cancellation/replacement and permission revocation. Return readable/writable ends in the correct direction, and avoid buffering unbounded clipboard payloads in memory or on disk.
5. **Explicit in-flight policy.** Portal XML does not promise that a late SelectionWriteDone is forbidden after deactivation; frontend deliberately lacks the current-access check there. Define cancellation versus draining for already-admitted transfers and preserve only the authority needed to finish them. Where revocation must stop bytes after FD handoff, keep a cancellable pump or equivalent controllable peer: closing an app's descriptor in the backend cannot close the app's duplicate. Test this policy instead of assuming dropping one FD revokes all copies. This is proposed lifetime engineering, not a new public API.
6. **Experimental integration before advertisement.** Keep actual service construction, tests and routing separate from capability claims. Current [main registration](/home/kevinard/projects/canopa/crates/canopa-portal/src/main.rs:478) and [normal portal descriptor](/home/kevinard/projects/canopa/packaging/portal/canopa.portal:1) contain no InputCapture/Clipboard advertisement. Do not add unavailable interface stubs or route normal clients to a partial service. Clipboard must be routed to a backend that owns the corresponding sessions; splitting it to an unrelated provider does not create a shared session registry.
